# 2026-07-29 (260729) 작업 로그

프로젝트: KFE 다이버터 솔버 오픈소스 대체 — Code_Aster 구조(FEM) 노드

> 이날까지는 서버(도커 사전빌드 이미지)로만 Code_Aster를 돌려왔다. 오늘 처음으로 **로컬 맥북에서 소스코드를 직접 컴파일해 실행**하는 파이프라인을 구축했다. 목적은 앞으로 `bibfor`/`bibcxx`/`bibc` 소스를 고치고 재컴파일해서 테스트하는 사이클을 로컬에서 돌리기 위함. 최적화 코드 변경은 아직 없음 — 오늘은 순수 빌드/실행 환경 구축.

## 오늘 한 일

1. **arm64 네이티브 시도 → 실패**: 이 맥북이 Apple Silicon(arm64)이라 처음엔 에뮬레이션 없이 네이티브로 빌드를 시도. `mfront`(재료거동 컴파일러) 패키지가 code_aster가 요구하는 버전대(`<5.0`)에서 conda-forge에 arm64 빌드가 없어서 실패. 강제로 5.0 이상 올리는 대신 안전하게 x86_64로 전환.
2. **x86_64 Docker 컨테이너로 전환**: Debian 12 컨테이너(linux/amd64, Docker Desktop의 Apple Silicon 에뮬레이션)에서 재시도.
3. **의존성 설치 (pixi + 공개 conda-forge)**: `pyproject.toml`에 EDF 사내망 전용 pypi 미러(`nexus.retd.edf.fr`)가 extra-index로 박혀 있어 사외 네트워크에서 접속 불가 → 주석 처리하고 공개 PyPI/conda-forge로 전체 의존성(MED, MUMPS, PETSc, HDF5, OpenMPI 등) 설치.
4. **컴파일 버그 2건 우회**:
   - `ar`(아카이버) 바이너리가 컨테이너에 없어서 컴파일러 감지 자체가 실패 → `apt install binutils`로 해결.
   - numpy import 시 QEMU 에뮬레이션 특유의 OpenMP 어서션 실패(`kmp_affinity.cpp` assertion) → `KMP_AFFINITY=disabled` 환경변수로 우회.
5. **`./configure` 성공** (3분 21초).
6. **실제 컴파일(`make install`) — 두 번 시도**: 첫 시도는 실수로 `-j1`(싱글스레드)로 돌아서 방치하면 수십 시간 걸릴 뻔함. 원인 파악(Make의 `$(MAKEFLAGS)` 셸 파싱 이슈) 후 `make -j10`으로 재시작 → **1시간 22분** 만에 9,977개 파일 컴파일/설치 완료.
7. **KFE 데이터셋 실행 — 두 번 시도**:
   - 1차: `memory_limit=8000`(8GB)로 실행 → 260만 자유도 행렬에 대해 MUMPS가 최소 5.3GB(out-of-core 기준)를 요구하는데 8GB로는 부족해 디스크 스와핑 지옥에 빠짐(`FACTOR_76` 경고). 1시간 넘게 진행이 없어 강제 종료.
   - 2차: `memory_limit=16000`(16GB)로 재시작 → 메모리 경고 없이 진행, **3시간 16분**(11,753초) 만에 정상 완료.
8. **결과 검증**: `peak.txt`의 폰미제스 최대응력이 **368.748 MPa**로, 이전에 서버에서 받아둔 golden 기준값과 **소수점까지 완전히 일치**.

## 판단 (오늘의 결론) ★

- **로컬 빌드+실행 파이프라인 확보**: 이제 소스 수정 → `pixi run make -j10` 재컴파일 → KFE 데이터로 실행/검증이 이 맥북에서 가능해졌다. 서버 접근이 안 될 때도 개발 사이클을 돌릴 수 있다는 게 오늘의 실질적 성과.
- **중요한 제약 재확인 (260728 로그와 교차 확인)**: 260728 상세 로그에서 이미 결론 낸 것처럼, 이번 KFE 케이스의 최대 병목(MUMPS 인수분해, 전체의 60\~90%대)은 **code_aster 소스가 아니라 서드파티 바이너리(MUMPS) 내부**에서 발생한다. 오늘 빌드한 것도 MUMPS는 conda-forge 사전빌드 패키지를 그대로 가져다 쓴 것이라 **컴파일한다고 그 병목 자체를 코드로 고칠 수 있게 되는 건 아니다.** 즉 오늘의 빌드 환경은 "컴파일이 되는가"를 확인한 것이고, 실제 속도 개선 레버는 여전히 (a) 솔버 설정값(RENUM, MPI 분배, PETSc 대안 등 — 260728에서 이미 927초→405~459초까지 줄인 바 있음)과 (b) code_aster 자체 코드가 차지하는 나머지 부분(메시 읽기, `LIAISON_MAIL` 접합조건 계산, 조립 등)에 있다.
- **맥북 실행 시간은 참고용일 뿐**: QEMU x86 에뮬레이션 + out-of-core 메모리 모드가 겹쳐서 3시간 16분이 걸렸지만, 이건 순수 계산 속도가 아니라 에뮬레이션/디스크 병목이 섞인 값이다. 실제 최적화 판단(전/후 비교)은 반드시 서버 숫자로 해야 한다는 원칙은 그대로 유지.

## 진행 중 / 이슈

- **메모리 설정 최적점 못 찾음**: 8GB는 부족, 16GB는 됐지만 여유가 넉넉한 수준은 아니었음(out-of-core 자체는 계속 필요 — MUMPS가 완전 in-core로 돌려면 54GB 요구). 다음에 같은 데이터로 돌릴 때는 처음부터 16GB 이상으로 설정할 것.
- **KFE 로컬 데이터셋의 `study.comm` 출처 재확인 필요** (260728 로그와 별개 이슈, 오늘 발견): golden 로그가 참조한 실행 파일명이 `study.comm.changed.py`이고 줄 번호가 현재 `study.comm`과 다르게 찍혀 있던 것을 확인했는데, 이는 `run_aster`가 실행 시 `.comm` 파일을 내부적으로 `.changed.py`로 복사해서 도는 정상 동작임을 이번 실행으로 확인함 (동일하게 우리 실행에서도 `study.comm.changed.py`가 찍힘). 즉 이전에 우려했던 "다른 파일일 수 있다"는 의심은 **해소됨** — 정상적인 run_aster 내부 동작이었다.
- **버전 불일치(17.4.0 vs 18.1.1)**: 위 표 참고. 서버와 동일 버전으로 맞출지, 아니면 최신 main 기준으로 계속 갈지 결정 필요.
